## 00. CORE WORKING RULES (user 2026-11-06, repeated because they were broken; these come before every other rule)
1. NEVER MAKE UP A RULE OR ASSUME ONE IS IN PLACE. Only Dave's rules (this file, his messages, the project docs) are rules. A threshold, cutoff, filter, limit or convention Claude would like to apply (for example "split a list only when it has 8 or more lines") is a PROPOSAL: say it to Dave, say that it is Claude's idea and not his, and wait for his answer. Never present an invented rule as an existing one, and never write one into a generator, linter or document without his approval. When unsure whether a rule exists, search the docs and ask; never assume.
2. NEVER DELETE PRIOR CONTENT WITHOUT ASKING DAVE FIRST. This covers library files, lines inside files, pools, docs and anything built from his source material. A filter that drops lines is deletion. Before any change that would remove content: list exactly what would go (every item, not a sample) and why, and wait for his yes. The default fix for a badly phrased line is to rephrase it, never to drop it.
3. VERIFY EVERYTHING, NOT SAMPLES. When a change touches many files or lines, compare before and after for every item (every place, every slot, every file) and report the full counts of what changed and what was lost. Random sampling is for reading quality only, never proof that nothing was lost.
4. TOO SHORT OR TOO BRIEF? ASK DAVE. When a line, list or entry seems too short, thin or fragmentary, ask him before doing anything, and treat enhancing it (adding detail from the source or from the wildcard system) as the better choice; deleting it is never the default.
5. ONE STEP AT A TIME, WITH THE COST STATED. Before any long job (a library rebuild is about 4 minutes, a full check about 5), say what it is, why, and how long, and wait for Dave's go. No chains of long jobs in one turn. Never start background jobs that outlive the reply.
6. NO PARALLEL OR REPEATED WEB REQUESTS. One request at a time to any site, never in a loop or in parallel, no retries without asking. GitHub is off limits entirely until Dave lifts the hold (his account was suspended on 2026-11-07 after a chat hit it like a bot).
7. READ THE RULES FIRST. At the start of every session and before any change to the library, read claude/STANDING_RULES.md and claude/HANDOVER_v109.md, and check a planned change against them before doing it.
8. SHORT REPLIES, NO JARGON. Plain words a normal reader understands (say "the automatic rule check", not "linter"). No work Dave has not asked for.
9. NEVER PRESUME AGES FROM A ROLE. ANY ADULT CAN APPEAR IN ANY SCENE OR SITUATION (Dave, 2026-11-07): 18-year-old volunteers, student teachers and student nurses included. This replaces the earlier 25-and-over limit for child-related places; those places stay entirely nonsexual. AGE IS NOT IMPORTANT beyond making someone an adult and describing the character themselves (Dave, 2026-11-07): never treat an age as clashing with a role, job or action, and never raise it as a problem.
10. DO NOT CHANGE THE WORDING OF EXISTING LINES (Dave, 2026-11-07): no rewording, rephrasing or "improving" of existing wildcard lines unless Dave explicitly asks for that specific change. A question from Dave gets an answer, not a change.
11. NO SPECIAL SYMBOLS (Dave, 2026-11-07): never "--", "---", "==", "===" or "|" in wildcard files or in prompts inside the release zips; those prompts are normal text with normal punctuation, quotes around text, and brackets. The "--prompt ... --steps ..." format is used only in the showcase files and in private test files made for Dave; documentation may also contain these symbols. Every other file, the sample prompt files included, is plain text. CHOICE BRACKETS ARE ALLOWED (Dave, 2026-11-07): "|" inside curly brackets, as in {a|b|c}, separates a limited set of choices that the wildcard tool and text encoder read, so files using that syntax (for example _tools/data/style_packs) stay as they are.
12. FILLED-IN TEXT ONLY IN SHOWCASE AND SAMPLE PROMPTS (Dave, 2026-11-07): wildcard files hold wildcard references for anything variable (quoted text uses the name and text pools, for example "__name_time__"), never typed-in fill. Showcase and sample prompt files are the only prompts in the system where the wildcards are expanded and the full text appears.
13. HOW THE SYSTEM FITS TOGETHER (Dave, 2026-11-07): everything except the showcase and sample prompts is connected wildcards, structured to fit the prompt files already in the system, and those prompts are designed around the most basic prompt structures. The prompts are kept alongside the wildcard files, and a prompt can itself become a wildcard inside a larger prompt. Any new or restored line must fit the slot sentence of the pool it goes into, and through it every prompt that uses that pool.

## 0. TEXT RULES (highest priority, set by the user 2026-11-04, repeated many times - never skip)
Source: MOSS_IMAGE_NOTES (our tests + OpenMOSS technical report). The model (text encoder Qwen3.5-9B) draws any word it is shown.
1. If text SHOULD appear on a sign, label, tag, packaging, badge, cap, t-shirt, card, book cover, poster, screen: write it verbatim in quotes, one line per text, say where it is ("on the first line", "on the second line"). Use the fake name system (name_* files) so the text is invented, not a real brand.
2. If text should NOT appear: do NOT mention it at all. Never write "no other words", "no readable text", "no lettering", "nothing else", "unlettered". Negations did not help in tests and the words invite lettering. Describe the surface positively: plain, unmarked, blank, decorated with shapes and patterns only.
3. Never mention label, tag, badge, sign, banner, wordmark, logo, slogan, caption, packaging text unless the text on it is defined in quotes.
4. Before every release, scan new/changed lines for undefined text mentions and for text negations. Report what was checked.
5. Brand styles are objects STYLED like a brand, never branded products: the file name carries the brand (maker_bs_heinz); the prompt text never names the brand, never says "in the style of <Brand>", and puts no logo/wordmark on every object. Style = colour, shape, material, pattern. A logo may appear small on packaging, labels or signs only. The object is already bought; it is not selling itself.
6. Fake names only: websites end in .example, phones use 555, no real brands/people outside maker_ files.

## 1. Content rules
- Natural-language prompts for txt2img (Moss Image). Everything fully described, never relying on a name or jargon alone; jargon described visually.
- All content from the wildcard system plus only joining words.
- Adult content: adults only, consensual; no minors or youth-coded wording (no school/student), no animals, diapers, real hate insignia, non-consent, NO urine/feces; knives/needles as objects only, never in use. Levels L1-L6 (L1-L5 four adults or fewer; L6 ejaculate/squirting/groups of five+); no crowds/audiences in L1-L5. Leave the six "...50..." prompt files as is.
